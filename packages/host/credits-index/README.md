# Credits host

English | [中文](README.zh.md)

## Summary

Use the signed-in product account for balance, recharge, usage analysis and media generation. Prompt assistance prepares editable image or video briefs without submitting media generation. Workspace video projects plan supported clips, generate them in order, and publish a locally verified final video. Paid requests use the current account; cancellation cannot guarantee that accepted upstream work stops billing.

## Use this package

The credits host relays account, balance, recharge and media operations through the origin-checked local `/credits` routes. The deployed API root is `https://8.133.202.230/harness`; model requests use its `/v1` suffix. The complete prefix is retained for every upstream request. This IP's root `/api` and `/v1` paths are rejected, redirects are not followed, and ordinary HTTPS certificate checks remain enabled.

### Account session

Phone challenge and login use `/api/user/phone/challenge` and `/api/user/phone/login` beneath the configured root. Login provides the short-lived management `access_token`, rotating refresh cookie and account-owned `relay_key`. Only that relay key authorizes model requests. The host stores these credentials privately, binds the session to its backend root, and waits for one shared renewal before using an expiring management token. Refresh and logout declare the backend's Origin. The host provides live `harnessAccount` authorization to the product model route; stored or environment credential references cannot replace a valid session. Logout removes this authorization immediately; a concurrent old refresh cannot restore it. Moving a stored session to another backend requires phone sign-in again.

Hosts sharing the same session file coordinate renewal and session mutations through file locks. Persisted renewal state shares cooldowns and rejected access credentials across cooperating Hosts; older client versions do not participate in these locks. An access token explicitly rejected with HTTP 401 is not reused even before its recorded expiry. A terminal renewal HTTP 401 clears only the captured account and credential epoch. Successful or rejected late responses cannot overwrite a newer login or clear its credentials. Disposal cancels recovery timers and HTTP work, then awaits exchanges and rejection-state writes. Reads or HTTP responses finishing after disposal cannot start renewal or clear the login. If background failure reporting throws, an independent warning reports the recovery failure without credentials.

`GET /credits/api/session` keeps its existing `ok`, `code`, `signedIn` and `liveness` fields. A stored login whose access cannot be confirmed remains `ACCOUNT_UNAVAILABLE`, `signedIn: true`, `liveness: 'unknown'`; this is a recoverable account-read result, not verified access or an invalid document. Optional `failure: { reason, stage, status? }` appears both at the top level and in `payload`. Its reasons distinguish `network`, `timeout`, `rate_limited`, `upstream_unavailable`, `upstream_rejected`, `protocol`, `identity_mismatch`, `renewal_unavailable` and `storage`; stages are `account-read` or `renewal`, and status is included only after observing an HTTP response. Renewal diagnostics are memory-only and bound to the exact credential epoch; an unobserved shared cooldown uses `renewal_unavailable`. No credential, remote body or exception text is included in these fields. Temporary failures preserve login and bounded renewal policy; confirmed terminal refresh401 returns signed-out immediately, including when it occurs during the live account read. Local lock or write failures while clearing an invalid stored login report a recoverable storage failure; protected requests remain blocked until invalidation succeeds.

Renewal recognizes HTTP 429 and `Retry-After` without requiring a JSON body, including older empty responses. Valid delay seconds or HTTP dates are honored; temporary HTTP 500/503 and transport failures keep the login and apply bounded exponential backoff. When cookie rotation is unconfirmed, retries of the old cookie stay within the API's 30-second recovery window and the configured retry budget. After either expires, the login remains stored, but recovery requires a newly confirmed cookie or signing in again; the old cookie is not replayed. This recovery never retries image, video or prompt-assistance generation POSTs.

`refreshRetryBaseDelayMs` defaults to 1000 and `refreshRetryMaxDelayMs` to 60000; both accept integer milliseconds from 1 to 2,147,483,647, with the maximum at least the base. A valid server `Retry-After` may exceed that local ceiling and is never shortened. `refreshRecoveryRetryLimit` defaults to 2 and accepts integers 0–5; it bounds additional exchanges after an unconfirmed rotation. The 30-second server recovery window is not a configurable client timeout.

Phone requests forward `idempotency_key`; redemption also forwards the opaque `challenge_id`. Before dispatch, the Host atomically saves the independent SMS and redemption keys in a private file bound to the complete backend root and phone. Recovery retains parameter fingerprints, challenge identifiers, server expiry and cooldowns, without the code or session credentials. OTP expiry removes the challenge record while an unconfirmed exchange keeps its original submission time, key and phone binding until confirmation; the API owns successful-response replay expiry. `/credits/api/session` includes non-secret pending recovery fields while signed out; `/credits/api/session/phone-recovery` reads the same state without dispatch. Unknown or pending delivery can only query the original SMS request. Only `delivery_status: not_sent` establishes definite non-delivery and permits a fresh key for an explicit new request. An unavailable response without that receipt retains the original key and reports unconfirmed delivery. Stable error codes select safe reports; raw provider errors remain private. A login response commits only with valid account, access expiry, relay credentials and the same-origin refresh cookie. Failed, incomplete and MFA-pending responses preserve the existing session, and delayed responses cannot undo logout. The Host reads API method options through `method` and `available`; only an available `2fa` flow completes through the same-origin security endpoint with a Host-only flow token. This existing endpoint has no new replay guarantee: an unknown result stops that flow and requires fresh phone authentication.

Desktop forwards content-free activity through authenticated `POST /credits/api/activity` to `/api/client-activity/heartbeat` beneath the same backend root. Only the current phone account authorizes reports. A random UUID separates each native process and login epoch; sign-out stops that epoch, and anonymous reports are discarded. The Host accepts only event, foreground, OS and app-version fields, never caller-selected user IDs. Failures are discarded without affecting model requests, balance, or sign-in; the server owns receive times and online expiry. Activity reads do not start credential renewal; the existing 60-second Host model-catalog timer renews the phone session while the application remains in the tray. Samples with expired access credentials are skipped until normal renewal completes.

Creation tools report only declared local failure codes, stages and exact known model IDs to `/api/client-errors` under the configured API root. Reports use the original account’s current access token, without prompts, paths, raw errors or caller-supplied identity. Reporting reads only the committed login cache, makes at most one attempt with two active requests and a three-second deadline, and never delays or retries generation. Signed-out, changed-account and capacity-overflow reports are discarded; old servers and rejected reports leave the original tool result unchanged. Background video-project failures use the same bounded reporter. The backend owns receive time, user identity and the separate client-error view. Client reports describe observed workflow outcomes, not platform-fault counts. Pending or unknown tasks cannot be reported as confirmed task or preflight failures; connection, HTTP status and cancellation codes are never inferred as `TASK_FAILED`. A transport timeout remains `TRANSPORT_TIMEOUT` without attributing its cause. Backend aggregation remains the server’s responsibility.

### Chat model refresh

Each product-route model listing first awaits the current account's `harnessAccount.refreshModels` result. The Host reads `/v1/models` with that account's relay key, excludes declared media generators, and synchronizes nonempty chat results before the adapter reads its configuration. Concurrent reads share one operation. An empty successful result exposes no chat models even if an older profile remains configured; unavailable reads become catalog failures instead of showing old models as currently available. Other provider routes keep their existing listing behavior.

The same refresh reads `GET <base>/api/status` for `data.client_model_config`, with `schema_version: 1`, `default_chat_model` and `model_order`. Explicitly ranked models appear first; unranked chat models retain their `/v1/models` order. Older backends may omit this configuration, which applies no deployment preference; failed reads or malformed configurations retain the last valid preferences. Reading these preferences submits no model requests and grants no additional model access.

The independent status sibling `client_model_presentation` has `{ schema_version: 1, models: { [exactModelId]: { description?, badge? } } }`. Its optional plain-text fields override the two model pickers independently: absence inherits local guidance and `""` hides that field. At most 256 model entries are accepted, with exact IDs of at most 255 UTF-8 bytes, descriptions of at most 500 UTF-16 units and single-line badges of at most 32. Descriptions retain line breaks; badges reject LF, CR, NEL, LS and PS. Unknown fields, nulls and malformed entries reject the display document without rejecting valid ordering/default preferences; each document keeps its own last-good value after failures. Missing display metadata or an empty map clears previous overrides. Last-good values belong to the exact backend, account and local login token, including changes committed by another Host sharing the session file; upstream access-token renewal under that login preserves them. Only currently authorized chat IDs on the configured product provider receive display text through `api-session/model-presentation`; other routes delegate unchanged. Display-only changes emit `api-session/model-catalog-changed`. Text never changes routing, capabilities, prices, model IDs or model requests.

New product profiles enable `followPolicy: true`: the default follows the backend preference only within the current account's authorized chat list. An empty, unavailable or media default falls back to the first available chat model after sorting. A successful manual `saveSelection` disables policy following; existing manual defaults and session-specific model selections remain unchanged. The [default-model service](../../core/agent-default-model/README.md) owns selection persistence.

Missing or empty model `input` declarations inherit the installed adapter catalogs only when the exact model ID has consistent nonempty input declarations across those catalogs. The confirmed product alias `yunshu-flash` inherits `deepseek-flash` inputs when it has no exact declaration; other aliases are not guessed. Discovery reads only installed providers in the same settings namespace, without contacting their endpoints. Explicit nonempty inputs and other model settings survive refresh and changes to the account's model list. Unknown or conflicting IDs receive no inferred image capability; an inherited image declaration describes the catalog, not a verified gateway request.

The product route uses the gateway's Chat Completions dialect: output caps travel as `max_tokens`, system instructions keep the `system` role, and requests omit `store`. Refresh preserves other compatibility settings and per-model overrides. Optional reasoning controls require that exact model's declared support; model aliases alone do not establish a reasoning format or effort range. Undeclared context and output capacities retain the adapter's configurable local working budgets, not verified upstream limits; the SDK sends its local output budget, bounded by estimated remaining context, even when the chat selects no explicit cap.

Startup and the 60-second timer use the same refresh operation. Committed sign-in, logout and local session expiry notify selectors immediately; discovery remains asynchronous and does not delay login. Successful refreshes notify changes in authorized model IDs, ordering or the effective default; unchanged reads do not notify. Login changes and logout cancel older discovery; commit checks the login generation, stored session identity, backend and expiry. Disposal cancels and awaits outstanding discovery. The UI can request a fresh catalog without waiting for the timer. Published pricing still describes media parameters, while the account's model endpoint determines its chat list; a declared or selected model can still fail upstream authorization or billing validation.

### Recharge

`POST /credits/api/recharge/wechat` accepts an integer `amount` in yuan and creates one Native order with the account's access token. The response exposes `outTradeNo`, `amount`, converted `points`, `expiresAt` and `qrCodeDataUrl`; raw quota is not a points amount. Conversion requires current status parameters before order submission. Unknown submission outcomes are reported without an automatic second order.

`GET /credits/api/recharge/wechat/order?outTradeNo=...` queries that same account's order. The host forwards the backend status without aliases and adds converted points. The client reports unknown states for manual checking instead of declaring success. Payment callbacks go directly to the deployed API, which owns crediting the account; the product only refreshes the live balance after a confirmed payment.

### Usage analysis

`GET /credits/api/usage?start=<seconds>&end=<seconds>` returns the signed-in account's hourly model aggregates. Both parameters are inclusive positive Unix-second integers; the complete interval may contain at most 31 days. The client chooses its display timezone before converting natural days to seconds. Duplicate parameters, account selectors, and other query parameters are rejected.

Success uses the credits envelope `{ ok: true, payload: ... }`. The payload contains `rows`, `start`, `end`, `asOf` (ISO read time) and `delayMinutes: 0`. Rows contain `timestamp`, `model`, `billingRecords`, `consumedPoints` and `totalTokens`. The host groups consumption log records by hour and model; the zero delay field describes the absence of the previous aggregate-export wait and does not guarantee immediate appearance of new charges. Consumption records are not request counts, and separately logged refunds are not subtracted.

The host verifies `/api/user/self` against the product session, then reads every page of `/api/log/self?type=2&p=1&page_size=100` for the selected interval. It validates pagination, account identity, quota and token fields, and the JSON-string `other` field. Failed, incomplete or inconsistent reads never produce partial rows. No administrator token, account search or deployment credential substitutes for the signed-in account.

A live `/api/status` read supplies `quota_per_unit` and `usd_exchange_rate`. Points use `quota / quota_per_unit × usd_exchange_rate × 1000`; neither backend parameter has a hardcoded fallback. Missing or invalid conversion settings and unavailable or invalid source data return `{ ok: false, code, message }` without a replacement zero. The client owns visible error reporting and retry and retains the previous display while a read is unavailable.

Usage reads share the local-origin guard, `timeoutMs` and the complete `newApiBaseUrl` deployment prefix. They use only the current account's access token. The product does not read cached quota or a different account's balance when the service is unavailable.

Chat-model point reads use each committed assistant attempt's exact gateway receipt and the current account's `/api/log/self?type=2&request_id=...` records. They verify `/api/user/self`, receipt endpoint, account and request identities, then convert the settled quota with live status parameters. Missing historical receipts or a different gateway are unavailable; missing ledger records remain pending without an invented zero or partial total. This amount covers only the selected session's model attempts, excluding image/video tools, standalone prompt assistance and separate child sessions. Reads never submit a model request or infer charges from tokens or account balance changes.

Authenticated `GET /credits/api/chat-usage` accepts one `session_id`, optional positive-integer `turn` and optional current `account_id`; it rejects duplicate, unknown and authority-bearing parameters. The Host reads the `chatReceipts` projection of an attached Session from its own store. This Host-only fold restores receipt and turn-state facts from committed events without retaining message content or adding Session events. An open turn is pending; missing Session lookup, attachment or projection is unavailable. Successful payloads contain `scope: 'chat-model'`, `status`, `accountId`, `settledRequests` and `totalRequests`; only `settled` includes finite nonnegative `points`. A changed login discards in-flight results before responding, and an explicit old `account_id` is refused.

Same-selection reads share a login-owned flight, while settled results, verified account/status context and exact-receipt quota share `chatUsageCacheTtlMs` (default 5,000 ms; range 1–60,000). Conversion parameters are refreshed from the server after that interval. Pending and unavailable results are not retained. Ledger requests across all selections share `chatUsageConcurrency` (default 4; range 1–8). Browser disconnection does not abort another consumer's flight. Login changes and logout immediately clear caches and abort old work; plugin disposal awaits aborted operations within `timeoutMs`. Each upstream JSON response is limited to 1 MiB.

### Prompt assistance

`POST /credits/api/prompt/assist` accepts exactly `{ accountId: string, sessionId: string | null, expectedSelection: { provider: string, model: string, reasoningEffort?: string } | null, kind: 'image' | 'video', prompt: string, instruction: string, references: string[], generation: Record<string, string> }`. The host compares `accountId` with the live product session and returns `ACCOUNT_CHANGED` before any model lookup when they differ; account and selection identifiers never become prompt text. The current draft, requested revisions, generation settings, and ordered `@图片1` reference labels with original filenames become model input; the same labels precede their image bytes and remain in the private request record. PNG, JPEG, and WebP references must be existing local `ma_` assets; arbitrary URLs, video, and client-selected routing or credentials are rejected. Images are inlined as chat image content. Uploads tagged to another account are rejected before dispatch; untagged legacy uploads retain their existing local behavior. A successful credits envelope contains `{ prompt, model }` in `payload`; failure contains a stable `code`, never an upstream body or exception. The client writes a candidate into the editable creation prompt only while the draft, account, session and chat selection still match; an unsuccessful request leaves the draft intact. Assistance does not submit media generation.

Assistance uses the current chat's durable model selection, or the current chat default when no explicit selection applies. The Host resolves the selection through the same chat catalog, requires the configured product provider and exact model, and checks image references against that model's declared image input capability. Browser `expectedSelection` detects stale requests; it cannot authorize a route. Missing services or unavailable models fail visibly; image-incompatible selections return `PROMPT_ASSIST_VISION_REQUIRED` without choosing a different model. Known video selections return `PROMPT_ASSIST_CHAT_REQUIRED` and ask the user to select a chat model. Legacy `promptAssistantModel` and `promptAssistantVisionModel` configuration remains accepted but does not select the model. Before each completion, the Host also checks `/v1/models` with the current account's relay key, rejects declared media generators and known video generators even when the gateway mislabels their endpoint, and rechecks the local chat selection and login identity before dispatch and before accepting a candidate. It calls `/v1/chat/completions` with that same key. For direct draft writing with `deepseek-flash`, `deepseek-v4-flash` or `deepseek-v4-pro`, it explicitly disables internal thinking with the documented `thinking.type` switch; the chat model and its stored selection remain unchanged, but the chat reasoning effort does not apply to this standalone writing task. Other models receive no DeepSeek-specific field. Expired sessions, missing sign-in or missing relay credentials stop the request; a deployment key is never a fallback. Background token renewal preserves the relay only when the upstream confirms the same account ID.

Request JSON is capped at 32 KiB; drafts at 7,000 characters; revision feedback at 2,000; parameter summaries at 16 string entries with 64-character keys and 256-character values. At least a draft, feedback, or reference is required. Up to nine distinct references may total 12 MiB, with a 6 MiB per-image cap; MIME and image signatures must match. Completion bodies and account catalogs are capped at 64 KiB, final prompts at 7,000 characters, and completions by `promptAssistantMaxTokens` (default 8,192; integer range 512–16,384). `promptAssistantTimeoutMs` covers the complete operation independently of other API deadlines; it defaults to 60,000 ms and accepts integer values from 1 to 120,000 ms; disconnect or plugin disposal cancels provider work, and disposal awaits settlement. Automatic provider retries are absent. After a completion is dispatched, timeout, transport failure, cancellation, or an upstream error returns `PROMPT_ASSIST_RESULT_UNKNOWN`: the result is unknown and billing may have occurred. Invalid completion data likewise reports possible billing; users should inspect usage before deciding to retry. Catalog-stage failures have not sent a completion.

Before a model call, the host saves `stateDir/prompt-assists/<random-request-id>/request.json` with the account ID, chat session, selected provider/model/effort, the actual thinking switch when used, token limit, exact system/user text, and reference metadata. Content-addressed image files under `prompt-assists/references` retain immutable bytes once per SHA-256 digest; ordinary uploads may overwrite an asset ID and are therefore insufficient for reconstruction. Directories use `0700`, files `0600` and exclusive creation. `outcome.json` stores the validated candidate or a safe failure code, whether a completion was dispatched, and private HTTP status, backend request ID and bounded structured error fields when available. A decoded completion also records its recognized finish reason and final-text and reasoning character counts, without retaining raw reasoning. Credential patterns and the current relay key are removed; free-form upstream bodies are excluded. Browser responses never include these diagnostics. The request ID correlates a forwarded failure with the backend error page. Input-record failure prevents sending; outcome-record failure returns `PROMPT_ASSIST_RESULT_STORAGE_FAILED`, indicating possible billing without an available candidate. A crash can leave a request without an outcome; records persist until an operator removes them, with no automatic retention cleanup. This standalone media workflow adds no Session format or agent-loop behavior.

### Published creation content

`GET /credits/api/creation/content` relays the deployed administration document as `{ ok: true, payload }`. `GET` and `HEAD /credits/api/creation/assets/:id` relay immutable `cc_` content-hash images and video, including single byte-range reads. These origin-checked reads use `newApiBaseUrl` and `timeoutMs`, send no account or deployment credential, reject upstream redirects and unexpected MIME types, and cap documents at 5 MiB and media at 100 MiB. Transfers stop on peer disconnect or plugin disposal; disposal awaits settlement. Errors expose only `CREATION_CONTENT_UNAVAILABLE`, never an upstream body. The [creation content reader](../../client/creation-content/README.md) owns document validation, refresh and consumer state.

### Announcements

Authenticated `GET /credits/api/announcements` reads the existing anonymous `/api/status` under `newApiBaseUrl`, sending no access token, relay key or cookie and following no redirects. It returns only `{ ok: true, payload: { enabled, items } }`; each item contains `content`, `publishDate` and an optional string `extra`. The public switch controls visibility; enabled empty and legacy-null lists remain empty. The API's returned order is retained, including future publication dates; this reader does not schedule publication. Missing support, HTTP failure, malformed data and transport failure remain distinct safe errors, never an empty success. Complete status bodies are limited to 1 MiB. Reads use `timeoutMs`, stop on disconnect or disposal, discard results after a login-epoch change and retain no announcement cache. The sidebar [announcement dialog](../../client/ui-settings-general/README.md#announcements) renders every content field as text.

### Customer support

Host-authenticated `GET /credits/api/customer-support` reads live `data.customer_service` schema 1 from anonymous `/api/status`, independently of product sign-in. The dedicated `enabled`, `qr_code_url`, `title` and `description` fields become `{ ok: true, payload: { enabled, qrCodeUrl, title, description } }`; disabled or empty QR settings clear every presentation field. Older APIs return `CUSTOMER_SUPPORT_UNSUPPORTED`; the login `wechat_qrcode` is never reused. Enabled text is plain, rejects control characters and is limited to 64 and 256 UTF-16 units. QR URLs are limited to 2048 UTF-8 bytes and accept credential-free HTTPS or the exact `/api/creation/assets/cc_<sha256>` path resolved under the complete deployment prefix; SVG and other schemes or relative paths are rejected. The Host fetches only status, never a configured image URL, and forwards no access token, relay key or cookie. Reads have the same 1 MiB bound and lifetime ownership as announcements, with distinct timeout, network, unavailable and invalid responses. The dialog retries by reading current settings; no previous QR is retained.

### Live generation activity

Generation statistics are independent of Desktop presence and gateway call logs. The Host observes live runtime ownership: a busy root chat, its child Agents and its owned creative jobs share one chat identifier; one project with eight clips contributes one project and eight submission attempts. Structured creation callbacks distinguish preparation, submission, acceptance, queueing, provider generation, saving, local editing and unknown results. A background tool return does not end its still-running creative chat. Interrupted local work does not establish that an accepted upstream task stopped. Video segments retain a private optional UUID attempt identifier; new executions persist it before submission, while explicit recovery fills missing legacy identifiers before querying and reuses original attempts without another POST. Reading old manifests does not migrate them or create live observations.

Reporting requires the current login's successfully acknowledged native presence UUID and the anonymous status document's explicit `client_activity_workload` capability. Complete, content-free snapshots go to `/api/client-activity/workload-snapshot` under the full API prefix with the current interactive access token, a monotonic sequence and terminal observations retained until acknowledgment. Chat, project and task counts remain separate; unavailable collections and unknown or expired observations never become measured zero. The Host sends no prompts, model details, progress text, paths or credentials in JSON, never renews login for telemetry, and pauses while access is uncertain. `generationActivityMinReportIntervalMs` coalesces changes (default 1,000 ms); `generationActivityReportIntervalMs` renews observations (default 30,000 ms); both use monotonic elapsed time. Older APIs receive only periodic capability reads and automatically resume collection after gaining support. Missing durable identities mark task collection unavailable. Complete snapshots are limited to 256 rows and 256 KiB; overflow pauses reporting without truncating counts or interrupting generation. Runtime read failures pause freshness until a successful complete read. Planned-shot bindings and independent local-operation observations remain explicitly uncollected; broad saving/editing stages do not invent them.

### Chat creation plans

Generation operations retain a Host-assigned `source`: `chat` for logged tools and `ai-creation` for manual composers. Confirmed chat invocations do not block AI Creation, whose pending submissions do not consume a chat request's video-work allowance. Both entries share account capacity. Each trusted chat generation request creates independent operations even when reusing a plan or prompt; earlier running or unknown operations do not lock the new request. Older operations keep their missing source and original receipts. Legacy video-project ids or tool-call origins can establish chat ownership; otherwise uncertain legacy work retains panel protection. Neither entry guesses ownership from titles or prompts.

When the skill registry is available, the bundled `yunshu-video-director` skill provides compact excerpts and adaptations of [cinematic-director](https://github.com/wuwangzhang1216/DirectorSKILL) and [video-storyboard-gen](https://github.com/anyhui/video-storyboard-gen-skill) for story, blocking, continuity, reference reconstruction, shots, dialogue and subtitles. [Source pins and adaptation details](third-party-notices/sources.json) and both complete MIT notices ship with this package. No community scripts or full reference libraries run or load at generation time. A simple single-clip brief goes directly to `generate_video_project` with actual Host defaults and no extra catalog or directing-skill model round; complex timing and directing use the catalog and skill. The legacy `generate_video` remains compatible. Deliberate story or continuity work uses an explicit creation plan, and longer videos use the same native project tool. Native tools own validation, submission, polling, downloads, editing, publication and recovery. Visual cuts do not each require a billed clip. Extra reference generation, alternate drafts and separate planning-model requests are not mandatory; upstream rendering time remains outside this workflow's control.

Narrative, advertising and multiple-reference video briefs use six Chinese sections: story overview; each real reference’s purpose and adopted or excluded elements; stable cast, relationships and scene style; a continuous shot timeline with actions, camera, dialogue windows, sound and music; continuity requirements; and prohibitions. Shot references retain the supplied image numbers. Explicit choices such as no subtitles take precedence, and speech that cannot fit the requested duration is flagged rather than silently sped up. Simple requests retain short answers. This shared guidance adds no planning completion or generated assembly code.

The shared director guidance asks chat and video AI writing to summarize platform or upstream failures in safe Chinese without reproducing HTTP responses, diagnostic JSON, codes, stacks, internal paths or credentials. Native image and single-video tool descriptions carry the same brief rules for chat calls that do not load the director skill. Confirmed sign-in, product-credit, file-validation and cancellation failures keep actionable recovery guidance. Unknown paid outcomes require checking existing tasks and artifacts before deciding whether to retry. Failed native image and single-video receipts preserve an available stable `code` beside their existing status and diagnostic message, so product views classify unknown outcomes without parsing upstream prose. These instructions preserve real tool results and required protocol fields, and do not restrict software or code diagnostics explicitly requested by the user. Failure summaries distinguish observed connection, timeout, validation, permission, rate-limiting, service and upstream-task categories. Connection interruptions, timeouts and unknown failures do not establish whether the cause is local, network, platform or upstream.

The separate `yunshu-minimax-h3` skill supplies locally authored H3 prompt notation based on the [official prompt-writing guide](https://github.com/MiniMax-AI/MiniMax-H3/tree/main/skills/h3-prompt-writing); the official skill files are not redistributed. Chat loads this notation only when needed for MiniMax-H3. Video AI writing adds the same notation only when `generation.model` is exactly `MiniMax-H3`, independently of the selected chat model. It separates exact tagged dialogue, ambient sound and background music, preserving dialogue and visible text in their original language. User-visible creation requirements, characters, materials, shots, scenes, camera movement, action and prompts default to Simplified Chinese unless the user explicitly requests another output language; English drafts do not change that default. Protocol keys, tags and resource identifiers retain their spelling. Other video models receive only the shared directing guidance, and image writing receives the same language rule without either video section. This selection requires no runtime guide download, translation request or extra completion.

`list_image_models` reads the current account’s authorized image catalog without submitting generation, uploading references or estimating prices. It intersects pricing/group capabilities with the account’s fresh model list and rechecks the initiating login before returning. Exact size strings retain pixel sizes or aspect ratios as published; named resolution tiers remain separate. Missing menus offer no choices, and unverified models expose only declared menus and conservative Host limits. The result also describes existing AI Creation controls; callers pass only fields accepted by `generate_image`. Authentication, permission, rate-limit, timeout, connection and unavailable-service failures remain safe read failures rather than empty catalogs or startup failures. No credential, header, provider route or raw exception enters the result.

`update_creation_plan` stores a complete image or video brief, stable character descriptions, identified source materials and ordered shots with camera, scene, action, exact dialogue and subtitle instructions. Every plan includes `kind`, `title`, `brief` and `shots`; every shot includes `id`, `order`, `title` and `prompt`. A shot title labels the plan and does not request on-screen text or subtitles. A revision names its explicit `plan_id` and cannot remove shots or image materials that already have generation records. Source paths are descriptive references, never authorization to read or preview arbitrary files; an empty source denotes material that has not been generated. Planning makes no provider request. `generate_image` and `generate_video` accept `plan_id` with `shot_id`; `generate_video_project` accepts `plan_id` with ordered `shot_ids`, one per actual supported clip. Alternatively, `generate_image` accepts `asset_id` instead of `shot_id` for an existing image material, including character references inside a video plan. Its real outputs belong to that material and its referenced characters, without appearing as finished shots or final videos. Missing, mismatched, duplicate-running or unknown-outcome associations fail before billing. Ordinary video submissions persist a credential-free receipt before dispatch and an accepted task id before polling. ### Local video editing

The project editor uses the Desktop-owned `DSH_VIDEO_RUNTIME_ROOT` directory and never searches PATH. It verifies both executables and an actual H.264/AAC encode in the selected output directory before paid generation, and refuses a read-only or escaping output tree. Every process runs through the current session’s subprocess provider and resolved sandbox policy, without shell interpolation. Inputs must be regular files inside the workspace or exact private clip directories already authorized by the project owner; private clip paths reject symbolic links. For current chat attachments stored outside the workspace, the model first copies the read-authorized attachments into the workspace through existing file tools. Protocol access is restricted to local files and pipes.

Editing preserves original clips, applies explicit start/end trims, fits each frame with padding inside the first clip’s canvas (or an explicit deployment override), rounded to even dimensions, converts to the configured frame rate, and normalizes audio to stereo 48 kHz. Missing audio becomes silence. Up to `videoEditSinglePassMaxInputs` inputs (integer 1–32, default 3) normalize and join decoded frames in one filter graph, then encode the final constant-frame-rate H.264/AAC video once. Each input has a one-thread decoder and its own local-file/pipe protocol restriction. Larger edits retain serial normalization and final encoding to bound simultaneous decoders. This editor does not add transitions, subtitles or music. An optional final duration trims the combined sequence and rejects insufficient footage. FFprobe checks the output duration before an exclusive, atomic same-volume publication; an existing destination is never replaced. Cancellation and deadlines terminate and await the managed process range before temporary-file cleanup. A failed edit publishes no candidate; any completed original clips remain available for a later editing attempt. Local process failures include a copyable diagnostic containing only the tool, operation stage, exit code, terminating signal and interruption kind when known; arguments, paths and child output stay private. Deadlines are reported as timeouts, and cancellation during executable resolution is not reported as a missing runtime. This saves local assembly time; it does not reduce upstream rendering time or verify generated dialogue, lip movements or subtitle quality.

The Host derives finished-video count and explicit duration only from the current human request. Workspace chat can create a finished video longer than the selected model's single-clip limit through `generate_video_project`. Each clip request retains the complete main brief as shared context and identifies only the current shot, its duration, and its allocated lines for generation. A shot prompt adds local direction instead of replacing the main brief. Combined prompts that exceed the provider limit fail before any paid submission; user text is never truncated. Existing saved projects resume their exact prepared requests.

For requested dialogue, the instructions distinguish stable speakers, exact spoken words and language, visible speech, off-screen narration, ambience, and background music. They preserve explicit silence and request subtitles only when the brief asks for them. H3-specific guidance follows its native dialogue format. These are generation requirements: the editor does not synthesize speech, align lips, or create subtitle tracks, and file verification does not establish that the requested dialogue or timing appeared in the rendered video.

Projects run as ordinary owned background jobs. Starting or resuming a project concludes that chat turn after returning canonical `job_id`, `project_id`, and `plan_seconds`, so another human request can proceed while generation continues. The agent presents the final file through the existing `present` tool and a clickable artifact link.

The server owns persistent waiting, shared admission and upstream recovery. A missing or disabled capability retains the legacy relay; an unreadable or inconsistent capability stops new work before POST. Queue support currently covers text-only requests and already supported persistent reference URLs. Original queue and gateway task reads remain available without new-work discovery or model catalog availability.

Only a verified cancellation before dispatch is reported as canceled. Dispatch conflicts, unknown results and legacy tasks retain their original IDs and may continue running and billing. The tool does not claim an upstream cancellation or refund. Ordinary `job_kill` remains local cancellation.

Independent clips can run concurrently within one project. Automatic scheduling uses four workers without a verified gateway ceiling and can follow a verified account pool up to sixteen; an explicitly configured `videoProjectConcurrency` sets a local upper bound. A verified lower limit still applies. The API owns atomic platform admission across accounts and users; an observed free-slot count is not a reservation. Accepted tasks are queried by their original IDs; unknown submissions are never repeated automatically. Final assembly follows the saved timeline order regardless of completion order. Client settings do not establish supplier capacity or configure upstream keys.

This describes an enforced pool ceiling, without proving supplier capacity, counting idle slots or reserving service. Absent or invalid video declarations use four workers; conflicting declarations cannot raise that default, while a verified lower limit remains effective. The current account model list must authorize the video model, and pricing must identify it as video. `MiniMax-H3` uses this same contract; four distinct enabled upstream keys with a verified pool ceiling of sixteen can use sixteen workers in automatic mode. Individual POSTs remain subject to actual gateway admission.

A saved record still marked `submitting` remains unconfirmed and blocks resubmission; a storage failure does not establish that upstream generation failed.

Each clip keeps its own queue or generation observation and elapsed waiting seconds; saving, saved, failed, uncertain and paused clips remain visible when another clip updates or final editing starts. These observations are transient; explicit resume reconstructs retained facts and queries original task IDs. Each run appends one final clip-state summary to ordinary job output, so `job_output` retains every clip’s outcome after finished jobs clear live progress, without logging every poll.

A per-clip deadline pauses observation and retains its task ID for explicit resume. Both settings accept integer milliseconds from 1 to 2,147,483,647; foreground limits do not truncate submission or saving. Busy responses without a task ID remain unknown, never confirmed queue admission, except for the gateway’s exact H3 capacity contract described below; no failed or timed-out POST is automatically repeated.

For exact `MiniMax-H3` requests, the following complete gateway contracts settle a rejected HTTP attempt: HTTP 429 with `h3_account_capacity_exhausted`, `submission_state: not_submitted`, `data: null`, `retryable: false`, `resubmittable: true` and no task id; or HTTP 502 with `h3_upstream_auth_rejected`, `submission_state: failed`, matching original `id`/`task_id`, `refund_confirmed: true`, `data: null`, `retryable: false` and `resubmittable: false`. Both finish the local attempt as failed and release its creation lock. Capacity rejection creates no task and incurs no generation charge; confirmed authentication failure retains the original failed task id and confirmed refund. The client does not repeat either POST. Failed project segments remain failed on resume, including after a restart; a new generation requires an explicit new attempt or project. Other 429/502 responses, incomplete markers and interrupted submissions remain uncertain. A 202 unknown response retains its original task id for GET-only recovery.

A gateway-confirmed unsent H3 attempt retains its HTTP status and safe business code, with exact `submission_code: h3_submission_not_sent`, `submission_state: not_submitted`, `upstream_submitted: false`, `retryable: false`, `resubmittable: true` and matching original `id`/`task_id`. Its `billing_state` must be `not_charged`, or `refunded` with `refund_confirmed: true`. A same-task GET can supply the same proof in `submission_receipt`; this ends only that retained local attempt and preserves its original task and request IDs. It does not set the local pre-submission flag or send generation again. Missing fields, conflicting identities and old unknown attempts without a task ID retain their lock. A confirmed rejection received while querying one project clip never changes another clip merely because its cancellation signal carries the same error.

Other image and video models use the separate `media_submission_receipt` proof. Schema version 1 binds the exact public model, media kind and original task IDs to `media_submission_not_sent`, `not_submitted`, `upstream_submitted: false`, `retryable: false`, `resubmittable: true` and the same task's canonical GET recovery path. `not_charged` permits no refund confirmation or `false`; `refunded` requires `true`. H3 and media proof fields cannot be combined. A verified proof ends the HTTP attempt as failed and preserves its original receipt; malformed or conflicting proofs remain unconfirmed instead of falling through to an ordinary failed status. No proof authorizes automatic resubmission.

The separate `media_submission_rejected` proof covers a request actually sent but explicitly refused by the upstream model. It requires HTTP 400 on create or HTTP 200 with `FAILURE` on the original GET, matching original identities, `upstream_submitted: true`, `provider_response_received: true`, exact reason `upstream_model_not_available`, and a confirmed refund. Its message distinguishes refusal from the unchanged never-sent proof. Ordinary upstream 404, timeout or capacity errors establish neither this proof nor permission to repeat generation.

Private owner-only records under H3 original-task queries use the fixed canonical `/v1/tasks/:id` route. A failed or cancelled response settles that exact original task only when HTTP 200 includes `provider_terminal_confirmed: true`, consistent original task identifiers and a matching terminal status, without conflicting submission or billing evidence. This confirms the provider outcome, not a refund, and never triggers another generation. Historical H3 failure statuses without this evidence remain unconfirmed.

`stateDir/video-projects/<project_id>/manifest.json` retain the account id, non-secret login fingerprint, calling chat and workspace, exact brief and prepared requests, ordered plan, accepted task ids, saved clip paths, and terminal outcome. Atomic replacement precedes each submission and follows each accepted task and saved clip; credentials and raw upstream responses are excluded. Optional local `title` and `shotTitles` retain output naming context; older records use their retained prompts. These labels do not enter provider requests. Clip originals remain in the private project cache for editing and resumption. Each verified clip and the final edit are also published to the captured save directory through artifact storage, so completed clips remain available in the artifact library even if a later segment fails. Older workspace-only projects publish clips under their original `videoProjectOutputDirectory`. Authorized project reads and `video_project_status` locally publish retained historical clips without submitting another generation request. A recoverable local copy failure keeps the authorized project visible with a publication warning; restoring the save directory or source file and refreshing retries the copy. Sandboxed local editing retains the final file inside the workspace before publication; returned media paths identify the published copies. Records and media have no automatic retention cleanup. `video_project_status` authorizes reads by account, chat, and workspace. A process restart leaves retained records rather than a fictional live job; explicit `resume_video_project` reuses saved clips and queries known task ids. Only projects whose manifest and actual request both select H3 may submit never-submitted remainder; non-H3 recovery needs a new generation request and model selection before further paid work. A submission without a persisted task id is an unknown, possibly billed outcome and is never automatically resubmitted; failed provider tasks likewise require a new explicit project or editing the retained clips.

Configure `videoProjectMaxSeconds` (default 300), `videoProjectMaxSegments` (32), `videoProjectConcurrency` (automatic when omitted, fallback 4; explicit integer 1–16), `videoProjectPollIntervalMs` (6000), `videoProjectTaskTimeoutMs` (900000), `videoProjectDownloadMaxBytes` (536870912), `videoProjectReferenceMaxBytes` (20971520 per local reference), and workspace-relative `videoProjectOutputDirectory` (`artifacts/videos`). The task timeout bounds each individual submission, original-task read and save; it is not a total generation deadline. Queue observations also honor the server's minimum poll interval. Transient original-task GET failures use the configured `videoQueryRetryLimit`; exhausting retries pauses observation with the original task retained, rather than declaring upstream failure or resubmitting. Content downloads use a complete-transfer deadline of at least 300000 ms, submission allows at least 180000 ms, while catalog and status requests retain `timeoutMs`. Interrupted content reads report `VIDEO_DOWNLOAD_UNAVAILABLE`, remove partial files and retain the known task for explicit resume without another submission. Complete records, including reserved task and path metadata, must fit 64 MiB before generation starts. These limits apply before paid work. Exact generation continuity depends on the provider; the pipeline supplies ordered shot prompts and shared references, but does not claim identity consistency or unseen transitions that the model has not generated.

Confirmed HTTP 403 rejections with the gateway’s exact `insufficient_user_quota` code are returned as `INSUFFICIENT_BALANCE` for image generation, single-video submission, video projects and AI writing. OpenAI envelopes must also carry the gateway’s `new_api_error` or Images `invalid_request_error` type. Upstream quota, channel debt, token limits, plain 403 responses and transport failures do not establish user balance exhaustion. A confirmed funding rejection stops the fixed video workflow and preserves saved clips. Because the gateway can also reject an adjusted cost after upstream acceptance, an unconfirmed submission stays unknown and cannot be automatically resubmitted, even after topping up. Native task-plugin responses which replace the code with `permission_denied` remain generic because the client cannot recover the original cause. No additional balance estimate or paid probe is sent.

## Model Experience

### Usage analysis

#### What the model sees

Usage analysis through `/credits/api/usage` is a browser-only read and contributes no model input.

#### Token effect

Usage reads make no model request and consume no model tokens.

#### KV Cache effect

Usage analysis does not change model context or KV cache.

### Prompt assistance

#### What the model sees

Prompt assistance makes one non-streaming completion using the selected chat model. Video assistance shares the director guidance used by the bundled chat skill for filmable story beats, consistent characters, shots, exact dialogue, lip movement and requested subtitle timing; these are generation requirements rather than verified output claims. Its system instructions and user text treat drafts, feedback, parameters, and images as untrusted reference material. The model returns a plain candidate prompt. Each revision sends the current edited candidate and new feedback rather than an implicit conversation history. Model-visible inputs and validated results remain reconstructable from the private standalone records described above.

#### Token effect

Each writing or revision request is billed to the current account and limits completion output to 2,048 tokens. Draft text, feedback, parameters and any reference images contribute input usage. The compact shared video guidance contributes input tokens; H3 notation is added only for that generation model, with no extra writing request.

#### KV Cache effect

Each explicit request supplies its own current draft and feedback without an implicit conversation history. This standalone workflow owns no provider cache.

### Video projects and editing

#### What the model sees

The read-only image catalog tool adds its declaration and, when called, exact model controls or a safe failure to ordinary logged tool history. Its generic read card labels the catalog operation. It adds no generation completion or hidden model input. The optional bundled director skill contributes its catalog description and, when loaded, directing and native-workflow instructions through the existing logged skill mechanism. The video tools, including `generate_video_project`, add planning, local editing, durable status, and explicit recovery instructions to the model context. Tool descriptions ask the agent to include exact dialogue, language, speaker and subtitle requirements. Per-clip provider prompts retain the main brief with current-shot scope and conditional audiovisual instructions. The agent must inspect the rendered result before claiming that speech, lip movements, or subtitles are present and synchronized. Shot prompts come from the logged tool input and the saved ordered brief. Existing job tools expose progress and final paths through their normal logged results. The video project records retain exact generation requests without changing the Session format or agent loop. The creation-planning tool records its structured input and returned plan id through ordinary tool history. Generation calls log their explicit plan and shot associations. Browser project reads and optional frame extraction add no model input, provider request or token usage; subsequent revisions remain explicit logged tool calls.

#### Token effect

Tool declarations, loaded skill text and logged results contribute ordinary agent-context tokens. The native workflow makes no extra chat-completion call; paid video-model calls follow the persisted clip plan.

#### KV Cache effect

Tool declarations and logged results follow ordinary Session request handling. Video generation and local editing add no implicit chat history and own no provider cache.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- The source groups records by hour and normally flushes them every five minutes. These aggregates cannot provide exact request timestamps, refund-adjusted net spending, per-token direction, or a live balance ledger. Usage responses are capped at 100,000 source rows; exceeding the cap is a visible failure.
- Video completion verifies saved files and duration, not speech content, lip synchronization, or subtitle accuracy. Local editing preserves the first audio stream of each clip; it does not merge separate voice and music tracks or preserve soft subtitle tracks.
