# Credits host

English | [中文](README.zh.md)

## Summary

Use the signed-in product account for balance, recharge, usage analysis and media generation. Prompt assistance prepares editable image or video briefs without submitting media generation. Workspace video projects plan supported clips, generate them in order, and publish a locally verified final video. Paid requests use the current account; cancellation cannot guarantee that accepted upstream work stops billing.

## Use this package

The credits host relays account, balance, recharge and media operations through the origin-checked local `/credits` routes. The deployed API root is `https://8.133.202.230/harness`; model requests use its `/v1` suffix. The complete prefix is retained for every upstream request. This IP's root `/api` and `/v1` paths are rejected, redirects are not followed, and ordinary HTTPS certificate checks remain enabled.

### Account session

Phone challenge and login use `/api/user/phone/challenge` and `/api/user/phone/login` beneath the configured root. Login provides the short-lived management `access_token`, rotating refresh cookie and account-owned `relay_key`. Only that relay key authorizes model requests. The host stores these credentials privately, binds the session to its backend root, and waits for one shared renewal before using an expiring management token. Refresh and logout declare the backend's Origin. The host provides live `harnessAccount` authorization to the product model route; stored or environment credential references cannot replace a valid session. Logout removes this authorization immediately; a concurrent old refresh cannot restore it. Moving a stored session to another backend requires phone sign-in again.

Desktop forwards content-free activity through authenticated `POST /credits/api/activity` to `/api/client-activity/heartbeat` beneath the same backend root. Only the current phone account authorizes reports. A random UUID separates each native process and login epoch; sign-out stops that epoch, and anonymous reports are discarded. The Host accepts only event, foreground, OS and app-version fields, never caller-selected user IDs. Failures are discarded without affecting model requests, balance, or sign-in; the server owns receive times and online expiry. Activity reads do not start credential renewal; the existing 60-second Host model-catalog timer renews the phone session while the application remains in the tray. Samples with expired access credentials are skipped until normal renewal completes.

### Chat model refresh

Each product-route model listing first awaits the current account's `harnessAccount.refreshModels` result. The Host reads `/v1/models` with that account's relay key, excludes declared media generators, and synchronizes nonempty chat results before the adapter reads its configuration. Concurrent reads share one operation. An empty successful result exposes no chat models even if an older profile remains configured; unavailable reads become catalog failures instead of showing old models as currently available. Other provider routes keep their existing listing behavior.

The same refresh reads `GET <base>/api/status` for `data.client_model_config`, with `schema_version: 1`, `default_chat_model` and `model_order`. Explicitly ranked models appear first; unranked chat models retain their `/v1/models` order. Older backends may omit this configuration, which applies no deployment preference; failed reads or malformed configurations retain the last valid preferences. Reading these preferences submits no model requests and grants no additional model access.

New product profiles enable `followPolicy: true`: the default follows the backend preference only within the current account's authorized chat list. An empty, unavailable or media default falls back to the first available chat model after sorting. A successful manual `saveSelection` disables policy following; existing manual defaults and session-specific model selections remain unchanged. The [default-model service](../../core/agent-default-model/README.md) owns selection persistence.

Missing or empty model `input` declarations inherit the installed adapter catalogs only when the exact model ID has consistent nonempty input declarations across those catalogs. Discovery reads only installed providers in the same settings namespace, without contacting their endpoints. Explicit nonempty inputs and other model settings survive refresh and changes to the account's model list. Unknown or conflicting IDs receive no inferred image capability; an inherited image declaration describes the catalog, not a verified gateway request.

Startup and the 60-second timer use the same refresh operation. Login changes and logout cancel older discovery; commit checks the login generation, stored session identity, backend and expiry. Disposal cancels and awaits outstanding discovery. The UI can request a fresh catalog without waiting for the timer. Published pricing still describes media parameters, while the account's model endpoint determines its chat list; a declared or selected model can still fail upstream authorization or billing validation.

### Recharge

`POST /credits/api/recharge/wechat` accepts an integer `amount` in yuan and creates one Native order with the account's access token. The response exposes `outTradeNo`, `amount`, converted `points`, `expiresAt` and `qrCodeDataUrl`; raw quota is not a points amount. Conversion requires current status parameters before order submission. Unknown submission outcomes are reported without an automatic second order.

`GET /credits/api/recharge/wechat/order?outTradeNo=...` queries that same account's order. The host forwards the backend status without aliases and adds converted points. The client reports unknown states for manual checking instead of declaring success. Payment callbacks go directly to the deployed API, which owns crediting the account; the product only refreshes the live balance after a confirmed payment.

### Usage analysis

`GET /credits/api/usage?start=<seconds>&end=<seconds>` returns the signed-in account's hourly model aggregates. Both parameters are inclusive positive Unix-second integers; the complete interval may contain at most 31 days. The client chooses its display timezone before converting natural days to seconds. Duplicate parameters, account selectors, and other query parameters are rejected.

Success uses the credits envelope `{ ok: true, payload: ... }`. The payload contains `rows`, `start`, `end`, `asOf` (ISO read time) and `delayMinutes: 0`. Rows contain `timestamp`, `model`, `billingRecords`, `consumedPoints` and `totalTokens`. The host groups consumption log records by hour and model; the zero delay field describes the absence of the previous aggregate-export wait and does not guarantee immediate appearance of new charges. Consumption records are not request counts, and separately logged refunds are not subtracted.

The host verifies `/api/user/self` against the product session, then reads every page of `/api/log/self?type=2&p=1&page_size=100` for the selected interval. It validates pagination, account identity, quota and token fields, and the JSON-string `other` field. Failed, incomplete or inconsistent reads never produce partial rows. No administrator token, account search or deployment credential substitutes for the signed-in account.

A live `/api/status` read supplies `quota_per_unit` and `usd_exchange_rate`. Points use `quota / quota_per_unit × usd_exchange_rate × 1000`; neither backend parameter has a hardcoded fallback. Missing or invalid conversion settings and unavailable or invalid source data return `{ ok: false, code, message }` without a replacement zero. The client owns visible error reporting and retry and retains the previous display while a read is unavailable.

Usage reads share the local-origin guard, `timeoutMs` and the complete `newApiBaseUrl` deployment prefix. They use only the current account's access token. The product does not read cached quota or a different account's balance when the service is unavailable.

Chat-model point reads use each committed assistant attempt's exact gateway receipt and the current account's `/api/log/self?type=2&request_id=...` records. They verify `/api/user/self`, receipt endpoint, account and request identities, then convert the settled quota with live status parameters. Missing historical receipts or a different gateway are unavailable; missing ledger records remain pending without an invented zero or partial total. This amount covers only the selected session's model attempts, excluding image/video tools, standalone prompt assistance and separate child sessions. Reads never submit a model request or infer charges from tokens or account balance changes.

Authenticated `GET /credits/api/chat-usage` accepts one `session_id`, optional positive-integer `turn` and optional current `account_id`; it rejects duplicate, unknown and authority-bearing parameters. The Host reads the `chatReceipts` projection of an attached Session from its own store. This Host-only fold restores receipt and turn-state facts from committed events without retaining message content or adding Session events. An open turn is pending; missing Session lookup, attachment or projection is unavailable. Successful payloads contain `scope: 'chat-model'`, `status`, `accountId`, `settledRequests` and `totalRequests`; only `settled` includes finite nonnegative `points`. A changed login discards in-flight results before responding, and an explicit old `account_id` is refused.

Same-selection reads share a login-owned flight, while settled results, verified account/status context and exact-receipt quota share `chatUsageCacheTtlMs` (default 5,000 ms; range 1–60,000). Conversion parameters are refreshed from the server after that interval. Pending and unavailable results are not retained. Ledger requests across all selections share `chatUsageConcurrency` (default 4; range 1–8). Browser disconnection does not abort another consumer's flight. Login changes and logout immediately clear caches and abort old work; plugin disposal awaits aborted operations within `timeoutMs`. Each upstream JSON response is limited to 1 MiB.

### Prompt assistance

`POST /credits/api/prompt/assist` accepts exactly `{ accountId: string, sessionId: string | null, expectedSelection: { provider: string, model: string, reasoningEffort?: string } | null, kind: 'image' | 'video', prompt: string, instruction: string, references: string[], generation: Record<string, string> }`. The host compares `accountId` with the live product session and returns `ACCOUNT_CHANGED` before any model lookup when they differ; account and selection identifiers never become prompt text. The current draft, requested revisions, generation settings, and ordered `@图片1` reference labels with original filenames become model input; the same labels precede their image bytes and remain in the private request record. PNG, JPEG, and WebP references must be existing local `ma_` assets; arbitrary URLs, video, and client-selected routing or credentials are rejected. Images are inlined as chat image content. Uploads tagged to another account are rejected before dispatch; untagged legacy uploads retain their existing local behavior. A successful credits envelope contains `{ prompt, model }` in `payload`; failure contains a stable `code`, never an upstream body or exception. The client writes a candidate into the editable creation prompt only while the draft, account, session and chat selection still match; an unsuccessful request leaves the draft intact. Assistance does not submit media generation.

Assistance uses the current chat's durable model selection, or the current chat default when no explicit selection applies. The Host resolves the selection through the same chat catalog, requires the configured product provider and exact model, and checks image references against that model's declared image input capability. Browser `expectedSelection` detects stale requests; it cannot authorize a route. Missing services or unavailable models fail visibly; image-incompatible selections return `PROMPT_ASSIST_VISION_REQUIRED` without choosing a different model. Known video selections return `PROMPT_ASSIST_CHAT_REQUIRED` and ask the user to select a chat model. Legacy `promptAssistantModel` and `promptAssistantVisionModel` configuration remains accepted but does not select the model. Before each completion, the Host also checks `/v1/models` with the current account's relay key, rejects declared media generators and known video generators even when the gateway mislabels their endpoint, and rechecks the local chat selection and login identity before dispatch and before accepting a candidate. It calls `/v1/chat/completions` with that same key. For direct draft writing with `deepseek-flash`, `deepseek-v4-flash` or `deepseek-v4-pro`, it explicitly disables internal thinking with the documented `thinking.type` switch; the chat model and its stored selection remain unchanged, but the chat reasoning effort does not apply to this standalone writing task. Other models receive no DeepSeek-specific field. Expired sessions, missing sign-in or missing relay credentials stop the request; a deployment key is never a fallback. Background token renewal preserves the relay only when the upstream confirms the same account ID.

Request JSON is capped at 32 KiB; drafts at 7,000 characters; revision feedback at 2,000; parameter summaries at 16 string entries with 64-character keys and 256-character values. At least a draft, feedback, or reference is required. Up to nine distinct references may total 12 MiB, with a 6 MiB per-image cap; MIME and image signatures must match. Completion bodies and account catalogs are capped at 64 KiB, final prompts at 7,000 characters, and completions by `promptAssistantMaxTokens` (default 8,192; integer range 512–16,384). `promptAssistantTimeoutMs` covers the complete operation independently of other API deadlines; it defaults to 60,000 ms and accepts integer values from 1 to 120,000 ms; disconnect or plugin disposal cancels provider work, and disposal awaits settlement. Automatic provider retries are absent. After a completion is dispatched, timeout, transport failure, cancellation, or an upstream error returns `PROMPT_ASSIST_RESULT_UNKNOWN`: the result is unknown and billing may have occurred. Invalid completion data likewise reports possible billing; users should inspect usage before deciding to retry. Catalog-stage failures have not sent a completion.

Before a model call, the host saves `stateDir/prompt-assists/<random-request-id>/request.json` with the account ID, chat session, selected provider/model/effort, the actual thinking switch when used, token limit, exact system/user text, and reference metadata. Content-addressed image files under `prompt-assists/references` retain immutable bytes once per SHA-256 digest; ordinary uploads may overwrite an asset ID and are therefore insufficient for reconstruction. Directories use `0700`, files `0600` and exclusive creation. `outcome.json` stores the validated candidate or a safe failure code, whether a completion was dispatched, and private HTTP status, backend request ID and bounded structured error fields when available. A decoded completion also records its recognized finish reason and final-text and reasoning character counts, without retaining raw reasoning. Credential patterns and the current relay key are removed; free-form upstream bodies are excluded. Browser responses never include these diagnostics. The request ID correlates a forwarded failure with the backend error page. Input-record failure prevents sending; outcome-record failure returns `PROMPT_ASSIST_RESULT_STORAGE_FAILED`, indicating possible billing without an available candidate. A crash can leave a request without an outcome; records persist until an operator removes them, with no automatic retention cleanup. This standalone media workflow adds no Session format or agent-loop behavior.

### Published creation content

`GET /credits/api/creation/content` relays the deployed administration document as `{ ok: true, payload }`. `GET` and `HEAD /credits/api/creation/assets/:id` relay immutable `cc_` content-hash images and video, including single byte-range reads. These origin-checked reads use `newApiBaseUrl` and `timeoutMs`, send no account or deployment credential, reject upstream redirects and unexpected MIME types, and cap documents at 5 MiB and media at 100 MiB. Transfers stop on peer disconnect or plugin disposal; disposal awaits settlement. Errors expose only `CREATION_CONTENT_UNAVAILABLE`, never an upstream body. The [creation content reader](../../client/creation-content/README.md) owns document validation, refresh and consumer state.

### Chat creation plans

When the skill registry is available, the bundled `yunshu-video-director` skill provides compact excerpts and adaptations of [cinematic-director](https://github.com/wuwangzhang1216/DirectorSKILL) and [video-storyboard-gen](https://github.com/anyhui/video-storyboard-gen-skill) for story, blocking, continuity, reference reconstruction, shots, dialogue and subtitles. [Source pins and adaptation details](third-party-notices/sources.json) and both complete MIT notices ship with this package. No community scripts or full reference libraries run or load at generation time. A simple finished short-clip brief goes directly to `generate_video`; workspace references can use `generate_video_project` even for a single clip. Deliberate story or continuity work uses an explicit creation plan, and longer videos use the same native project tool. Native tools own validation, submission, polling, downloads, editing, publication and recovery. Visual cuts do not each require a billed clip. Extra reference generation, alternate drafts and separate planning-model requests are not mandatory; upstream rendering time remains outside this workflow's control.

Narrative, advertising and multiple-reference video briefs use six Chinese sections: story overview; each real reference’s purpose and adopted or excluded elements; stable cast, relationships and scene style; a continuous shot timeline with actions, camera, dialogue windows, sound and music; continuity requirements; and prohibitions. Shot references retain the supplied image numbers. Explicit choices such as no subtitles take precedence, and speech that cannot fit the requested duration is flagged rather than silently sped up. Simple requests retain short answers. This shared guidance adds no planning completion or generated assembly code.

The shared director guidance asks chat and video AI writing to summarize platform or upstream failures in safe Chinese without reproducing HTTP responses, diagnostic JSON, codes, stacks, internal paths or credentials. Native image and single-video tool descriptions carry the same brief rules for chat calls that do not load the director skill. Confirmed sign-in, product-credit, file-validation and cancellation failures keep actionable recovery guidance. Unknown paid outcomes require checking existing tasks and artifacts before deciding whether to retry. Failed native image and single-video receipts preserve an available stable `code` beside their existing status and diagnostic message, so product views classify unknown outcomes without parsing upstream prose. These instructions preserve real tool results and required protocol fields, and do not restrict software or code diagnostics explicitly requested by the user.

The separate `yunshu-minimax-h3` skill supplies locally authored H3 prompt notation based on the [official prompt-writing guide](https://github.com/MiniMax-AI/MiniMax-H3/tree/main/skills/h3-prompt-writing); the official skill files are not redistributed. Chat loads this notation only when needed for MiniMax-H3. Video AI writing adds the same notation only when `generation.model` is exactly `MiniMax-H3`, independently of the selected chat model. It separates exact tagged dialogue, ambient sound and background music, preserving dialogue and visible text in their original language. User-visible creation requirements, characters, materials, shots, scenes, camera movement, action and prompts default to Simplified Chinese unless the user explicitly requests another output language; English drafts do not change that default. Protocol keys, tags and resource identifiers retain their spelling. Other video models receive only the shared directing guidance, and image writing receives the same language rule without either video section. This selection requires no runtime guide download, translation request or extra completion.

`update_creation_plan` stores a complete image or video brief, stable character descriptions, identified source materials and ordered shots with camera, scene, action, exact dialogue and subtitle instructions. A revision names its explicit `plan_id` and cannot remove shots or image materials that already have generation records. Source paths are descriptive references, never authorization to read or preview arbitrary files; an empty source denotes material that has not been generated. Planning makes no provider request. `generate_image` and `generate_video` accept `plan_id` with `shot_id`; `generate_video_project` accepts `plan_id` with ordered `shot_ids`, one per actual supported clip. Alternatively, `generate_image` accepts `asset_id` instead of `shot_id` for an existing image material, including character references inside a video plan. Its real outputs belong to that material and its referenced characters, without appearing as finished shots or final videos. Missing, mismatched, duplicate-running or unknown-outcome associations fail before billing. Calls without a plan create their own minimal record, so successful chat generation is still discoverable; no call selects a latest project implicitly.

Image reconstruction and subsequent video generation can use existing uploaded `ma_` ids or generated image output ids/paths owned by the same explicit plan. The Host reads only that exact account/chat/workspace record, verifies the saved image and materializes its bounded bytes as a local uploaded reference before normal provider validation. This supports an artifact destination outside the workspace without granting a new filesystem root. An `asset_id` is a planning label, never a provider reference id; preview URLs and arbitrary paths are not image references. Existing workspace video references keep their ordinary filesystem authorization.

`generate_image` can edit an image from the calling chat's current user attachments, identified by its exact attachment id or projected read-only path, without first copying it into the workspace. The attachment store verifies the saved bytes; another chat's images and arbitrary attachment paths grant no access. Readable workspace images retain normal path containment and file checks. The Host materializes these bounded images as private `ma_` references, then sends supported edits as multipart `image[]` to `/v1/images/edits` beneath the complete configured API prefix using the current account relay key. The selected image model must declare edit support; models without edit support are not silently enabled for edits.

`yunshu-internal-gpt-image-2` uses a separate task contract shared by chat and AI creation. The Host validates up to six authorized PNG/JPEG/WebP references, each at most 10 MiB, before uploading any. It sends each image to authenticated `POST /v1/uploads/images` with multipart `model` and `file`, then submits verified HTTPS receipt URLs under `files.toapis.cn/uploads/` or `files.toapis.com/uploads/` as `reference_images` to `/toapis/v1/images/generations`. Generation carries only `model`, `prompt`, `n: 1` and optional `reference_images`; the server controls output settings, and pixel size or other OpenAI knobs are not forwarded. Receipts require matching MIME and size, a nonempty id, and URLs without credentials, query or fragment. Both paths retain the deployment prefix and use only the current account relay key. An invalid file, failed upload or invalid receipt names the original file and stops before generation. Uploads and generation are never automatically resubmitted; ordinary OpenAI edits retain their existing multipart route.

Before revising a retained project, `get_creation_plan(plan_id)` returns the complete bounded planning fields using the same names as `update_creation_plan`. Account, chat and workspace ownership apply to this read. It excludes execution requests and login data, changes no state, and makes no provider request; targeted revisions preserve unrelated characters, materials and shots from this authoritative read.

Image submissions use `imageSubmitTimeoutMs` (default 180000 ms); complete submission, polling and saving use `imageTaskTimeoutMs` (600000 ms). Status reads retain the independent `timeoutMs` deadline (15000 ms), wait `imagePollIntervalMs` (2000 ms) between reads, and allow `imageQueryRetryLimit` (2) consecutive transient retries. Generation POSTs are never retried. The Host retains the original request ID as soon as response headers arrive and commits an accepted task ID before polling. Cancellation, query interruption and download failure preserve a known task for read-only recovery; stopping local waiting does not cancel upstream work or establish a refund. A submission without a confirmed task remains unknown and must not be resubmitted automatically.

The image outcome reports `submission_state`, `plan_id`, `operation_id` and available task/request ids. `query_image_task` without an operation id lists this account and chat’s unresolved receipts; with the original plan and operation ids it queries and saves that task. The authenticated creation panel uses `POST /credits/api/creative/image/recover` to start the same read-only upstream recovery. Final settlement retains the latest receipt atomically if an earlier receipt write stopped. Pending or unknown image-panel records block a new panel submission in the same conversation across reloads. A confirmed pre-submit interruption does not hold that lock. See the [receipt ownership decision](../../../.agents/notes/implemented/bug-fix/2026-10-21-image-task-receipt-recovery.md).

Private versioned records at `stateDir/creative-projects/<project_id>/project.json` bind plans and invocation outcomes to the account, chat and workspace. Atomic owner-only writes precede paid submission and retain each image immediately after saving, including partial batches. Account or login changes reject late writes and late preview completions. The existing video manifest remains authoritative for long-video tasks, saved clips, editing and final completion; records reference it rather than parse progress prose or duplicate its state. Single-generation calls retain a dispatch marker before the possible charge: after restart an unfinished dispatched call is unknown, while a prepared-only call is interrupted. The latest explicit attempt determines each shot's status while older outputs remain accessible; an unknown charge remains visible and blocks another submission for the affected shot. Explicit recovery preserves concurrent plan revisions and saved materials. Neither listing nor opening a project starts or resumes generation.

Authenticated Host clients read `GET /credits/api/creative/projects?session_id=...`, returning `{ ok: true, payload: { accountId, projects } }` with the credential-free [browser types](src/creative-types.ts). Both account and exact chat filter the result. `GET` and `HEAD /credits/api/creative/media` require the session, project and recorded output ids, plus an optional extracted-frame index; paths in query parameters never authorize reads. Media supports single byte ranges and refuses missing or symlinked files and replacements detected during opening. Media reads recheck the original account and login epoch before starting a response; signing out or changing accounts during a read rejects a response that has not started. Sign-out returns `AUTH_REQUIRED`. Invalid records and unavailable storage return safe visible failures instead of an empty success.

Each projection includes a plan-only `planRevision`, its owning `sessionId`, retained operation `tasks` and completed/total shot counts. Material images, generated shot clips and final files enter the combined output list with actual-path deduplication. Planned `durationSeconds` remains editable independently of `actualDurationSeconds`, the latest submitted duration. `POST /credits/api/creative/plan` accepts `{ session_id, project_id, expected_revision, change }` for a bounded shot edit, reorder, character/material upsert or explicit removal. It performs no generation. A stale revision returns `CREATIVE_PLAN_STALE` with HTTP 409; running linked members and retained execution associations are protected. `GET`/`HEAD /credits/api/creative/reference` reads only the exact plan's uploaded image material through `session_id`, `project_id` and `asset_id`, with account checks before sending bytes.

Current AI image/video composer requests include `session_id` and `account_id`. The Host requires its authenticated connection, the same signed-in account and that exact live workspace chat before submission, then retains an independent minimal project and actual saved outputs through the same store as chat. It never guesses the latest project. Old requests omitting both association fields retain their earlier media contract. Plugin disposal cancels and awaits owned panel generation; an accepted upstream task can still continue billing.

Committed video clips and final videos receive three real JPEG samples through the session's sandboxed bundled FFmpeg editor. Preview frames remain under the original workspace's `.yunshu-creative/previews`; a preview failure sets `previewUnavailable` while preserving the real video and its generation outcome. Plans and records are bounded to 2 MiB, 64 characters, 128 materials or shots, and 256 invocations per project; listings are bounded to 1,000 retained project directories and 8 MiB of project projections. There is no automatic retention cleanup. Character consistency, spoken words, lip movements and subtitle timing remain unverified requirements until the rendered output is actually inspected.

### Video capabilities and references

Video submission and status reads use the selected capability's `route`; an explicit pricing route takes precedence. MiniMax-H3 uses `POST /v1/video/generations` and `GET /v1/video/generations/:id`, while other video models retain their existing protocol. Generic task responses under `data` accept uppercase `NOT_START`, `SUBMITTED`, `QUEUED`, `IN_PROGRESS`, `SUCCESS`, and `FAILURE`. Completed files are read through `/v1/videos/:id/content`, retaining the configured `/harness` prefix and the current account relay key. A channel's chat test does not verify video generation.

Video menus read explicit `seconds` or `duration` declarations from public pricing `parameters` (a field map or JSON Schema `properties`), then `billing_usage_schema`. Numeric enums or finite `minimum`/`maximum` ranges select whole seconds from 1 to 3600 and override the model table; exclusive bounds and `multipleOf` further restrict the menu. Missing, malformed or unbounded declarations retain the known model limits; billing examples never grant durations or additional reference slots. Resolution enums and constants follow the same live priority. The current H3 response only declares a numeric seconds field without bounds, so its known 4–15-second menu remains. A model appearing in public pricing does not establish that a particular account can generate with it.

A declared `oneOf` pairs `properties.resolution.const` or `.enum` with bounded `properties.seconds` or `.duration`. The resulting `durationByResolution` menus govern both panel requests and project planning; missing resolution keys are unavailable, and a resolution must be selected. For example, a producer may explicitly publish one branch for 480P/768P at 4–30 seconds and another for 2K at 4–15 seconds. This describes supported parsing, not a declaration that the running API or an unspecified upstream supports those combinations. The Host rejects unsupported combinations and fractional or nonnumeric durations before model submission.

Local `POST /credits/api/assets` identifies image bytes independently of filename or MIME hints, decodes PNG/JPEG/JFIF/WebP/AVIF/GIF/BMP/TIFF/HEIC/HEIF, applies orientation, and produces a model-safe PNG or JPEG. Original images may be up to 32 MiB and 40 million pixels; normalized images are limited to 6 MiB each and 12 MiB per generation. Animated and multipage sources explicitly use their first frame. The response retains the original name, actual source format, dimensions, normalized MIME/size and conversion facts; structured failures name the upload without exposing decoder errors. `GET`/`HEAD /credits/api/assets/preview?asset_id=...` serves normalized bytes with host authentication, the uploading account and `Cache-Control: no-store`. Video and audio uploads still require matching MIME/signatures, limited to 32 MiB and 15 MiB respectively. A generation accepts at most 48 MiB of total reference bytes and a 64 MiB encoded request. H3 combines references in one complete `metadata.content` array; first/last frames cannot be mixed with generic reference slots, and adaptive ratio needs actual image/video input. Media validation does not verify upstream generation quality.

Chat tools accept `reference_audios` as uploaded asset ids or readable workspace WAV/MP3 paths. Video projects retain these references for recovery. The optional `audio` request uses a provider switch only when the selected model declares that switch. H3 has fixed native audio: `audio: true` is accepted without adding an unsupported request field, while `audio: false` is rejected before submission.

### Artifact destinations

When the composition provides the optional [artifact storage service](../../deliverables/artifacts-index/README.md), images, downloaded media and single videos capture the current destination before generation or saving. All outputs from that operation retain the same destination even if the user changes the setting. New video projects persist the captured publication directory; editing stays inside the workspace sandbox, then the Host copies the completed file into that directory without replacing existing files. Publication failure retains source clips and the staged final video for explicit recovery, without repeating completed paid submissions. Local video edits use the same publication service.

Without this service, images and single videos keep `stateDir/media`, and video projects keep the workspace output directory. Older project records without a publication directory retain their original workspace behavior when resumed. Changing a preference never moves existing files or rewrites old chat paths.

### Local video editing

The project editor uses the Desktop-owned `DSH_VIDEO_RUNTIME_ROOT` directory and never searches PATH. It verifies both executables and an actual H.264/AAC encode in the selected output directory before paid generation, and refuses a read-only or escaping output tree. Every process runs through the current session’s subprocess provider and resolved sandbox policy, without shell interpolation. Inputs must be regular files inside the workspace or exact private clip directories already authorized by the project owner; private clip paths reject symbolic links. For current chat attachments stored outside the workspace, the model first copies the read-authorized attachments into the workspace through existing file tools. Protocol access is restricted to local files and pipes.

Editing preserves original clips, applies explicit start/end trims, fits each frame with padding inside the first clip’s canvas (or an explicit deployment override), rounded to even dimensions, converts to the configured frame rate, and normalizes audio to stereo 48 kHz. Missing audio becomes silence. Up to `videoEditSinglePassMaxInputs` inputs (integer 1–32, default 3) normalize and join decoded frames in one filter graph, then encode the final constant-frame-rate H.264/AAC video once. Each input has a one-thread decoder and its own local-file/pipe protocol restriction. Larger edits retain serial normalization and final encoding to bound simultaneous decoders. This editor does not add transitions, subtitles or music. An optional final duration trims the combined sequence and rejects insufficient footage. FFprobe checks the output duration before an exclusive, atomic same-volume publication; an existing destination is never replaced. Cancellation and deadlines terminate and await the managed process range before temporary-file cleanup. A failed edit publishes no candidate; any completed original clips remain available for a later editing attempt. This saves local assembly time; it does not reduce upstream rendering time or verify generated dialogue, lip movements or subtitle quality.

<a id="video-projects"></a>
### Video projects

Workspace chat can create a finished video longer than the selected model's single-clip limit through `generate_video_project`. The planner first minimizes billable clip count, then surplus seconds: a 40-second request uses `15 + 15 + 10` when those values exist, or three fixed 15-second clips trimmed to 40 seconds. It validates every shot request and the local editor before the first paid submission. Optional shot prompts must match the planned clip count; uploaded reference ids and readable workspace media are checked through the current session. Generation uses only the signed-in account's relay credential and checks the captured account and login before each submission. Sign-out, expiry, or login change stops further charges.

An explicit `shot_durations_seconds` sequence uses exactly those supported per-shot durations and requires their sum to equal the requested total. A linked creation plan supplies its saved timeline timing when every selected shot has a duration; incomplete timing requires correction instead of silently replanning. Without explicit shot prompts, the fixed workflow assembles each selected shot's saved scene, camera, action, exact dialogue, subtitles and character directions. It adds only that shot's linked image materials and character references, preferring their latest actual generated image. Every reference and duration is validated before the first charge; no extra planning or translation model call and no agent-written assembly script is used. Retained projects resume their exact prepared requests.

Each clip request retains the complete main brief as shared context and identifies only the current shot, its duration, and its allocated lines for generation. A shot prompt adds local direction instead of replacing the main brief. Combined prompts that exceed the provider limit fail before any paid submission; user text is never truncated. Existing saved projects resume their exact prepared requests.

For requested dialogue, the instructions distinguish stable speakers, exact spoken words and language, visible speech, off-screen narration, ambience, and background music. They preserve explicit silence and request subtitles only when the brief asks for them. H3-specific guidance follows its native dialogue format. These are generation requirements: the editor does not synthesize speech, align lips, or create subtitle tracks, and file verification does not establish that the requested dialogue or timing appeared in the rendered video.

Projects run as ordinary owned background jobs. The tool returns canonical `job_id`, `project_id`, and `plan_seconds`; existing job tools report progress and cancellation. Final success contains only independently verified, saved `final_path` and clip paths. The agent presents the final file through the existing `present` tool and a clickable artifact link. A local cancellation stops subsequent submissions and local work; an already accepted upstream task may continue running and billing because the relay exposes no cancellation operation.

Private owner-only records under `stateDir/video-projects/<project_id>/manifest.json` retain the account id, non-secret login fingerprint, calling chat and workspace, exact brief and prepared requests, ordered plan, accepted task ids, saved clip paths, and terminal outcome. Atomic replacement precedes each submission and follows each accepted task and saved clip; credentials and raw upstream responses are excluded. Clip originals remain in the private project cache for editing and resumption. Each verified clip and the final edit are also published to the captured save directory through artifact storage, so completed clips remain available in the artifact library even if a later segment fails. Older workspace-only projects publish clips under their original `videoProjectOutputDirectory`. Authorized project reads and `video_project_status` locally publish retained historical clips without submitting another generation request. A recoverable local copy failure keeps the authorized project visible with a publication warning; restoring the save directory or source file and refreshing retries the copy. Sandboxed local editing retains the final file inside the workspace before publication; returned media paths identify the published copies. Records and media have no automatic retention cleanup. `video_project_status` authorizes reads by account, chat, and workspace. A process restart leaves retained records rather than a fictional live job; explicit `resume_video_project` reuses saved clips and queries known task ids before any never-submitted remainder. A submission without a persisted task id is an unknown, possibly billed outcome and is never automatically resubmitted; failed provider tasks likewise require a new explicit project or editing the retained clips.

Configure `videoProjectMaxSeconds` (default 300), `videoProjectMaxSegments` (32), `videoProjectPollIntervalMs` (6000), `videoProjectTaskTimeoutMs` (900000), `videoProjectDownloadMaxBytes` (536870912), `videoProjectReferenceMaxBytes` (20971520 per local reference), and workspace-relative `videoProjectOutputDirectory` (`artifacts/videos`). Content downloads use a complete-transfer deadline of at least 300000 ms, while catalog, submission and status requests retain `timeoutMs`; the original job cancellation and per-clip deadline still bound downloads. Interrupted content reads report `VIDEO_DOWNLOAD_UNAVAILABLE`, remove partial files and retain the known task for explicit resume without another submission. Complete records, including reserved task and path metadata, must fit 64 MiB before generation starts. These limits apply before paid work. Exact generation continuity depends on the provider; the pipeline supplies ordered shot prompts and shared references, but does not claim identity consistency or unseen transitions that the model has not generated.

Confirmed HTTP 403 rejections with the gateway’s exact `insufficient_user_quota` code are returned as `INSUFFICIENT_BALANCE` for image generation, single-video submission, video projects and AI writing. OpenAI envelopes must also carry the gateway’s `new_api_error` or Images `invalid_request_error` type. Upstream quota, channel debt, token limits, plain 403 responses and transport failures do not establish user balance exhaustion. A confirmed funding rejection stops the fixed video workflow and preserves saved clips. Because the gateway can also reject an adjusted cost after upstream acceptance, an unconfirmed submission stays unknown and cannot be automatically resubmitted, even after topping up. Native task-plugin responses which replace the code with `permission_denied` remain generic because the client cannot recover the original cause. No additional balance estimate or paid probe is sent.

## Model Experience

### Usage analysis

#### What the model sees

Usage analysis through `/credits/api/usage` is a browser-only read and contributes no model input.

#### Token effect

Usage reads make no model request and consume no model tokens.

#### KV Cache effect

Usage analysis does not change model context or KV cache.

### Prompt assistance

#### What the model sees

Prompt assistance makes one non-streaming completion using the selected chat model. Video assistance shares the director guidance used by the bundled chat skill for filmable story beats, consistent characters, shots, exact dialogue, lip movement and requested subtitle timing; these are generation requirements rather than verified output claims. Its system instructions and user text treat drafts, feedback, parameters, and images as untrusted reference material. The model returns a plain candidate prompt. Each revision sends the current edited candidate and new feedback rather than an implicit conversation history. Model-visible inputs and validated results remain reconstructable from the private standalone records described above.

#### Token effect

Each writing or revision request is billed to the current account and limits completion output to 2,048 tokens. Draft text, feedback, parameters and any reference images contribute input usage. The compact shared video guidance contributes input tokens; H3 notation is added only for that generation model, with no extra writing request.

#### KV Cache effect

Each explicit request supplies its own current draft and feedback without an implicit conversation history. This standalone workflow owns no provider cache.

### Video projects and editing

#### What the model sees

The optional bundled director skill contributes its catalog description and, when loaded, directing and native-workflow instructions through the existing logged skill mechanism. The video tools, including `generate_video_project`, add planning, local editing, durable status, and explicit recovery instructions to the model context. Tool descriptions ask the agent to include exact dialogue, language, speaker and subtitle requirements. Per-clip provider prompts retain the main brief with current-shot scope and conditional audiovisual instructions. The agent must inspect the rendered result before claiming that speech, lip movements, or subtitles are present and synchronized. Shot prompts come from the logged tool input and the saved ordered brief. Existing job tools expose progress and final paths through their normal logged results. The video project records retain exact generation requests without changing the Session format or agent loop. The creation-planning tool records its structured input and returned plan id through ordinary tool history. Generation calls log their explicit plan and shot associations. Browser project reads and optional frame extraction add no model input, provider request or token usage; subsequent revisions remain explicit logged tool calls.

#### Token effect

Tool declarations, loaded skill text and logged results contribute ordinary agent-context tokens. The native workflow makes no extra chat-completion call; paid video-model calls follow the persisted clip plan.

#### KV Cache effect

Tool declarations and logged results follow ordinary Session request handling. Video generation and local editing add no implicit chat history and own no provider cache.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- The source groups records by hour and normally flushes them every five minutes. These aggregates cannot provide exact request timestamps, refund-adjusted net spending, per-token direction, or a live balance ledger. Usage responses are capped at 100,000 source rows; exceeding the cap is a visible failure.
- Video completion verifies saved files and duration, not speech content, lip synchronization, or subtitle accuracy. Local editing preserves the first audio stream of each clip; it does not merge separate voice and music tracks or preserve soft subtitle tracks.
